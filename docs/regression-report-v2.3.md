### 서머타임·법정시계 범위

- `clock: 'korea-legal'`을 명식 계산에 적용했다. 서머타임(1948·1949·1950·1951·1955~1960·1987·1988)과 1954-03-21~1961-08-09의 UTC+8:30이 함께 보정된다.
- 1955~1960년은 기준 오프셋이 +8:30이고 서머타임이 +1시간이라, 단순 “−1시간” 보정으로는 30분이 어긋난다. 엔진의 법정 시계 표를 쓰는 이유다.
- 보정한 명식에는 “그 시기 한국 법정 시계로 보정했어요” 문장이 붙는다(명식 접기 안).

### 자시 처리

- 자시(23:00~00:59)는 입력 폼에서 **자정 넘긴 00시대(조자시) / 전날 밤 23시대(야자시)** 를 고르게 했다.
- 기본값은 조자시(00:30). 23:30 고정으로 인한 “입춘 전날 밤 출생이 다음 날로 계산되는” 오류를 없앴다.
- 시진 안에 절입이 있으면 `termEdge`로 고지한다(1982-02-04 입춘 12:45, 1984-02-05 입춘 00:19 등).

## 4. 문장↔근거 추적

- 무료 문장은 `content/free.js` 카탈로그에서 `requires`/`forbids`로만 선택된다.
- 근거 칩은 선택된 문장의 `requires` Finding `display.short`에서 자동 생성된다(`render/select.js basisOf`). v2.2의 `basisFor()`는 삭제했다.
- 실측 예: 2000-01-01 오시 무료 화면 — 근거 “일간 무토 · 일간 흙 ↔ 불 · 나를 낳는 기운 · 불 3 · 흙 3 · 편인·정인 3 · 대운 己卯”. 모든 칩이 해당 문장의 requires에 존재한다.
- 유료 성향 상세는 `content/paid.js`의 새 문단(월령·지장간·동률 각도)을 쓴다. 무료 성향 36문단과의 중복 **0**.
- 상충 해석(동률)은 `ELEM.TIE.*` Finding을 requires로 갖는 문장만 쓴다. 단정 문장은 `ELEM.MAX.*`를 요구하므로 동률에서 선택되지 않는다.

## 5. 궁합(인연 궤도)

- `compatibility()`는 일간·일지 index 두 값만 읽는다. 같은 두 값을 가진 “최소 명식”과 전체 명식의 결과가 동일함을 확인했다.
- `evidence[]`(일간 글자·일지 글자·천간합/충·육합/충)를 반환하고, 점수에는 “제품 규약 점수” 라벨을 붙였다.
- 8×8 조합에서 점수 18~98, 궤도 1~3 범위를 벗어나지 않았다.
- `/r/{code}`: CSPRNG 12자(base32, 60bit), TTL 30일, revoke 토큰. D1에는 `ds`·`db`·`revoke_hash`만 저장한다. Worker 테스트 5건 통과.

## 7. 실패했거나 남은 것

1. **원본 QA의 성별**: 화면에 성별이 없어 여성으로 가정했던 것을, QA06·QA09·QA11만 남성으로 바로잡아 재검증했다(§9). 나머지 9건은 여성 가정을 유지한다.
2. **자시 분 단위**: 폼은 시진 단위다. 00:10과 00:50을 구분하지 못하므로, 절입이 시진 안에 있으면 `termEdge` 고지로 처리한다. 분 입력은 다음 판본 후보.
3. **월지 격국·신강신약**: 규칙안만 작성했고 앱 판정에는 넣지 않았다(`docs/gyeokguk-singang-proposal.md`). 사용자 승인 전 구현 금지.
4. **궁합 문장의 Finding화**: 근거 데이터(`evidence`)는 내보내지만, `ORBIT_TYPE` 문장 자체는 아직 `copy.js`의 자유 문자열이다.
5. **Worker 배포**: `/api/share`·`/r/{code}`는 코드·테스트만 있고 실제 D1 마이그레이션·배포는 하지 않았다. 그래서 친구 초대 버튼은 **‘준비 중’**으로 잠겨 있다(`window.NYANG_INVITE_READY`, 기본 false). 배포 뒤 `wrangler d1 execute … --file=schema.sql` → `wrangler deploy` → `index.html`의 스위치를 켠다.
6. **`main` 브랜치**: v2.3.1에서 `v2.3` → `main` 병합·푸시하고 GitHub Pages 라이브에 반영했다.

### 9.2 친구 초대 — Worker 배포 전 ‘준비 중’

- `window.NYANG_INVITE_READY === true`일 때만 초대 링크를 만든다. 라이브 기본값은 false.
- 버튼 이름이 `친구 초대 · 준비 중`(점선), 안내 문구가 “아직 준비 중이에요. 그동안은 이름·생년월일로 궤도에 직접 올려 보실 수 있어요.”로 바뀐다.
- 누르면 **준비 중 안내 토스트**만 나온다. `/api/share` 요청 0건, 콘솔 오류 0건(`parseInvite`도 조회를 시도하지 않는다).
- 결과 카드의 ‘친구 초대 링크도 함께 넣기’ 체크박스도 잠긴다(점선, ‘· 준비 중’).
- 개인정보 URL 폴백은 그대로 없다 — 준비 중에는 링크를 만들지 않고, 예전 `?inviter=` 링크는 안내만 한다.
- 테스트는 `ctx.add_init_script("window.NYANG_INVITE_READY = true")`로 Worker 배포 상태를 흉내 내어 초대 왕복을 계속 검사하고, 별도 컨텍스트에서 기본(준비 중) 상태를 검사한다.

### 9.3 궤도 숫자 점수 제거 · 일주 근거 표시
