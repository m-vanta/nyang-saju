# 검토용 마스터 문서

> 목적: **실제 모델 호출 전에**, 이 실험의 설계가 검토 가능한 상태인지 외부 검토자가
> GitHub `exp/ai-engine` 브랜치에서 바로 확인할 수 있게 한다. API 키는 필요 없다.
> 모든 수치는 이 브랜치의 산출물이며, 문서와 코드가 어긋나면 `run.mjs` 자기시험이 실패한다.

## 0. 30초 요약

- **무엇을 비교하나**: 같은 모델·같은 설정에서 **입력만** 바꾼 다섯 실험군.
  A 규칙 기반(현행 앱) · B 명식만 · C +analysisData · D +명리 지식베이스 · E D+비평·재작성.
- **무엇을 재나**: 8섹션 해석 문서의 근거 정합(EA-1·EA-2), 상충 설명(CA), 환각(HZ),
  금지 판정(GA), 스키마(SC), 사실 모순(CR), 일반론(GN), 문단 품질(judge 근사), 비용·지연.
- **무엇을 막나**: 신강·신약 점수화, 격국 단정, 용신 임의 판정, 없는 간지·십성·합충 창작,
  근거 없는 단정, 민감 주제 판정, 개인정보.
- **현재 상태**: 오프라인 스텁으로 전 구간 통과. **실제 API 호출은 하지 않았다.**

1. `analysisData` 에 판정 필드(`verdict`·`strength`·`score`)가 없는가. → `NyangAnalysis.lint()` 가 12/12 통과.
2. 지장간 표가 藏遁歌와 맞는가. → `docs/myeongri-literature-verification.md` §2.

## 3. ② 명리 지식베이스 (실험군 D/E 입력)

- 위치: `docs/myeongri-knowledge-base.md` (자동 생성) · `tests/ai-compare/lib/knowledge-base.mjs` (원본)
- 규모: **35항목** — 문헌 확인 15 · 현대적 해석 8 · 제품 규약 12
- 분류: 월령 4 · 지장간 4 · 통근 3 · 투출·격국 8 · 십성 4 · 생극제화 2 · 합충 3 · 대운·세운 4 · 해석 금지선 3

### 표기 3단계 (핵심)

| 표기 | 뜻 | 검사 |
|---|---|---|
| [문헌 확인] | 원문에 그 문장이 있거나 원문 표에서 직접 읽힌다 | `source.quote` 필수 |
| [현대적 해석] | 고전에 그 문장이 없다. 오늘의 언어로 옮긴 해석 관행 | `source` 금지 |
| [제품 규약] | 냥도사가 정한 계산·표기 규칙 | `source` 금지 |

### 항목 예시

- `KB-GEOK-02` [문헌 확인] 兼透則兼用 — 『자평진전』論雜氣如何取用 「一透則一用，兼透則兼用，透而又會，則透與會並用。」
- `KB-ROOT-01` [문헌 확인] 통근 輕重 — 『적천수천미』衰旺 「長生祿旺，根之重者也；墓庫餘氣，根之輕者也。」
- `KB-PER-04` [현대적 해석] 세운·대운과 명식의 상호작용은 조건으로만 — 엔진이 계산하지 않는 합·충을 만들지 않는다.
- `KB-HID-04` [제품 규약] 지장간 가중치 100/70·30/60·30·10 — 문헌 근거 없음, `product/1` 라벨.
- `KB-GUARD-01` [제품 규약] 신강·신약 점수·격국 단정·용신 임의 판정 금지.

### 검토 포인트

1. [문헌 확인] 항목의 인용이 실제 원문과 맞는가. (선행 문서의 출처 링크 사용)
2. [현대적 해석] 항목이 문헌처럼 읽히지 않는가. (문장에 "~로 읽는다"만 있고 출처가 없다)
3. [제품 규약] 이 문헌 근거인 척하는 곳이 없는가.
4. 빠진 개념이 있는가 — 특히 **대운·세운 상호작용**은 제품 규약·현대 해석으로만 덮여 있다.
5. 35개로 D/E 에 충분한가, 아니면 과한가(프롬프트 토큰·비용).

## 4. ③ B/C/D/E 프롬프트

- 원본: `tests/ai-compare/lib/prompts.mjs` (`systemPrompt`, `userPrompt`, `SECTION_TASKS`, `CRITIQUE_DIMENSIONS`)
- 실행 산출물의 프롬프트 전문: `out/<runId>/blind/prompts.md` (비밀 — 평가 후 공개)
- 프롬프트 버전: `p/1.0` · temperature 0 · max_tokens 8000

### 입력 경계 (실험의 유일한 축)

| 실험군 | 시스템 프롬프트의 입력 안내 | 사용자 프롬프트에 들어가는 것 |
|---|---|---|
| B | "명식 기본표만 주어진다. analysisData·대운·세운·지식베이스는 없다" | `chartBasics`, `evidenceRefs`(chart.\*) |
| C | "analysisData 와 대운·세운이 주어진다. 지식베이스·판정은 없다" | + `analysisData`, `period`, `evidenceRefs`(analysis.\*) |
| D | "analysisData·대운·세운·지식베이스가 주어진다. 표기를 구분해 인용하라" | + `knowledgeBase`(35항목 압축), `kbRefs` |
| E | "너는 비평자 겸 재작성자다" | D 와 같음 + `draft`(D 초안) + `critiqueChecklist` |

### 엔진 원칙 (시스템 프롬프트 10개)

1. 사실 계산은 코드가 한다 — 입력에 없는 간지·십성·지장간·합충을 만들지 않는다.
2. 여러 요소의 상호작용을 종합 해석한다 — 나열 금지.
3. 두 요소가 다른 방향이면 양쪽 + 조건.
4. 문단마다 `evidenceRefs` ≥1.
5. 근거가 부족하면 `status:"unavailable"` + 이유.
6. 신강·신약·용신·격국 확정 금지, 점수 창작 금지.
7. 문단마다 그 사람의 사실 ≥1 (바넘 금지).
8. 같은 근거 반복 금지.
9. 명리 용어 뒤에 생활 언어.
10. JSON 만 출력.

### 8섹션 과제

① 천기팩폭 ② 대표 성향 ③ 내면의 상충하는 성향 ④ 반복되는 행동 패턴
⑤ 연애운 ⑥ 재물운 ⑦ 직업운 ⑧ 대운 및 올해 운세

- 섹션별 목표·문단 수·금지 규칙은 `SECTION_TASKS` 에 있다.
- ③은 상충 축이 없으면 비운다. ⑧은 `period` 가 없으면 비운다.

### E 의 비평 축 (6개)

명리 오류 · 논리 비약 · 상충 해석 누락 · 바넘 효과 · 개인화 부족 · 수위·톤.
E 는 `critique[]`(지적)와 수정된 `sections[]` 를 함께 낸다.

### 검토 포인트

1. B 프롬프트에 analysisData 가 새지 않는가. → 자기시험 `B 는 analysisData 를 받지 않는다` 가 검사.
2. D 프롬프트가 지식베이스를 "문헌처럼" 쓰도록 부추기지 않는가. → 표기 구분 지시 확인.
3. E 가 초안에 없는 사실을 더하지 않도록 막혀 있는가. → "초안의 근거 ID 범위 안에서만" 지시. **검증기는 E 의 초안 대비 추가 사실을 직접 비교하지 않는다**(개선 후보).
4. 8섹션이 유료 7챕터로 자연스럽게 조립되는가. → `docs/paid-7-chapters-spec.md` §1.

결정적으로 판정 가능한 것만 '반려'로 만든다. 실패하면 `feedback`(고칠 점)을 붙여 재시도한다.

## 10. 검토 요청 (구체적으로)

1. **지식베이스 충실성** — [문헌 확인] 15항목의 인용이 원문과 맞는가. 틀린 것·과장된 것을 지목해 달라.
2. **표기 경계** — [현대적 해석]·[제품 규약]이 문헌처럼 읽히는 항목이 있는가.
3. **프롬프트** — B/C/D/E 차이가 실험 축 하나로만 갈리는가. D 프롬프트가 KB 를 과신하게 만드는가.
4. **E 의 범위** — "초안에 없는 사실을 더하지 않는다"를 검증기로 강제할 방법(현재 미구현).
5. **검증기 오탐/미탐** — V4~V6 의 정규식 한계, V15 마커 목록, 한국어 수사 처리.
6. **8섹션 분해** — 유료 7챕터로 조립하기에 부족/중복인 섹션이 있는가.
7. **상충 의무(O1~O6)** — 이 여섯 축이 명리적으로 타당한가. 빠진 축(예: 형·파·해, 공망)이 있는가.
8. **비용** — 12건 × 5실험군 × (재시도) 기준 추정이 현실적인가. 캐시 전략이 빠져 있다.
9. **평가지표** — judge 근사가 실제 품질과 상관 있을 만한가. 사람 평가 설계(블라인드 패키지)가 충분한가.
10. **누락** — 신살·공망·궁합 점수처럼 일부러 뺀 개념이 제품에 필요한가.

## 11. 알려진 한계

- 오프라인 스텁은 **문장 품질을 재지 않는다**. 배선·검증기·채점·비용 경로만 검증한다.
- judge 는 결정적 근사이며 모델 채점·사람 채점과의 상관을 확인하지 않았다.
- V4 는 한자 쌍만 검사한다(한글 간지 오류 미검출).
- E 의 "초안 대비 추가 사실" 검사가 없다.
- 블라인드 패키지에 토큰·비용이 들어가 프롬프트 길이를 암시할 수 있다(완전 블라인드는 아님).
- E 의 비평 기록은 '비평이 있는 응답 = E'를 드러내므로 패키지에서 빼고 `blind/critique.md`(비밀)로 분리했다.
- `--mode full` 실호출은 승인 전까지 실행하지 않았다. 실제 비용·지연·품질은 미측정.
- O1(월령↔통근)은 QA01~12 에서 발동하지 않는다 — C1 픽스처로만 확인 가능.
