> GitHub `exp/ai-engine` 브랜치에서 바로 확인할 수 있게 한다. API 키는 필요 없다.

## 0. 30초 요약

- **무엇을 비교하나**: 같은 모델·같은 설정에서 **입력만** 바꾼 다섯 실험군.
  - **A** 규칙 기반(현행 앱 카탈로그) — 기준선
  - **B** 기본 명식 + 대운·세운 (모델 자체의 명리 지식 허용)
  - **C** B + `analysisData`
  - **D** C + 명리 지식베이스 35항목
  - **E** D + D 초안 비평·재작성
- **무엇을 재나**: 8섹션 해석 문서의 근거 정합(EA-1·EA-2), 상충 설명(CA), 환각(HZ),
  금지 판정(GA), 스키마(SC), 사실 모순(CR), 일반론(GN), 문단 품질(judge 근사), 비용·지연.
- **무엇을 막나**: 신강·신약 점수화, 격국 단정, 용신 임의 판정, 없는 간지·십성·합충 창작,
  근거 없는 단정, 민감 주제 판정, 개인정보.
- **자동 검증의 경계**: 구조·참조 검증(근거 ID 실재·입력 범위)과 결정적 내용 검증(사실 오류·
  금지 표현·상충)만 한다. **자동 통과는 명리학적 해석 품질을 보증하지 않는다.** 품질은
  블라인드 3종(고객·명리·기술) 평가의 몫이다.
- **현재 상태**: 오프라인 스텁으로 전 구간 통과(A~E gate 전부 PASS). **실제 API 호출은 하지 않았다.**

## 4. ③ B/C/D/E 프롬프트 (p/1.1)

- 원본: `tests/ai-compare/lib/prompts.mjs`
- 실행 산출물: `out/<runId>/blind/prompts.md` (비밀) · 호출별 전문 `out/<runId>/calls/*.json`
- temperature 0 · max_tokens 8000

### 입력 경계 — 실험의 유일한 축

| 실험군 | 사용자 프롬프트에 들어가는 것 | 시스템 프롬프트의 경계 안내 |
|---|---|---|
| **B** | `chartBasics`(간지·오행 개수·표면 십성·12운성·지장간), **`period`(대운·세운)**, `evidenceRefs`(chart.\*·period.\*) | "analysisData·지식베이스는 없다. **네가 아는 명리 지식을 활용해 종합 해석해도 된다.** 계산된 사실과 네 해석을 구분하고, 입력에 없는 간지·합충·개수를 만들지 않는다." |
| **C** | + `analysisData`, `period`, `evidenceRefs`(analysis.\*) | "지식베이스·규칙 판정은 없다. 사실 사이의 관계는 네가 종합한다." |
| **D** | + `knowledgeBase`(35항목), `kbRefs` | "표기([문헌 확인]/[현대적 해석]/[제품 규약])를 구분해 인용한다." |
| **E** | D 와 같음 + `draft`(D 초안) + `critiqueChecklist` | "비평자 겸 재작성자. 초안에 없는 사실을 더하지 않는다." |

- **B 를 바꾼 이유**: 예전 B 는 명식 기본표만 받아 대운·세운이 없었고, `chart.*` 만 인용한 문단이
  일반론으로 채점됐다. 그 설계에서는 B 의 실패가 '지식베이스 효과'가 아니라 '입력 결손'이었다.
  이제 B 는 코드가 정확히 계산한 기본 명식과 대운·세운을 받고, 모델 자체의 명리 지식을 쓰도록
  허용된다. C/D 와의 차이는 **analysisData(사실) → 지식베이스(문장)** 하나씩만 남는다.
- **자기시험**: B 프롬프트에 `analysisData`·`knowledgeBase` 가 없고 `period.seun` 이 있는지,
  근거가 `chart.*`·`period.*` 뿐인지 매 실행 확인한다.
- **C·D 경계 자기시험**: D 프롬프트에서 `knowledgeBase` 만 빼면 C 프롬프트와 완전히 같아야 한다
  (근거 목록 제외). 이 검사가 실패하면 두 실험군의 차이가 하나가 아니라는 뜻이다.

### E 의 실행 조건

- E 는 **유효한 D 초안**(호출 성공·JSON 파싱 성공·검증기 통과)이 있을 때만 돈다.
- D 가 없으면 `skipped_no_d`, D 가 실패·무효면 `skipped_no_valid_d:<이유>` 로 건너뛰고 리포트 §건너뜀에 남는다.

### 4.6 A 실험군 콘텐츠 출처

A 는 앱의 문장 카탈로그를 쓰지만, 8섹션 그릇에 담으면서 **앱 화면에 없는 문단을 실험이 만든 경우**가 있다. 그것을 숨기면 A 가 실제 서비스와 같은 것으로 읽히므로 섹션·문단마다 `contentOrigin` 을 붙이고 리포트에 표로 낸다.

| 출처 | 섹션 | 뜻 |
|---|---|---|
| `service` | §01·§02 | 앱 화면 문장 그대로(무료 팩폭·성향, 유료 상세) |
| `service-mapped` | §04·§05·§06·§07 | 유료 화면의 반복 패턴·세 가지 운 문장을 8섹션 자리로 옮겨 담음 |
| `experimental-generated` | §03·§08 | 앱에 없는 자리 — 상충 문단과 기간 종합 문단은 규칙 엔진이 새로 만듦 |

이 구분은 블라인드 고객·명리 패키지에는 넣지 않는다(A 임이 드러난다). `blind-key.json`·`tech-eval` 에만 둔다.

## 6. ⑤ 검증기 규칙 (V1~V21) — 구조·참조와 내용을 분리

검증 결과는 두 묶음으로 나뉘어 리포트·score.json에 기록된다.

- **구조·참조 검증** = V1(스키마)·V2(근거 존재)·V3(근거가 입력 범위 안)·V13(KB 참조)
  → "이 문단이 실재하는 근거 ID를 달았는가"만 본다. 계산으로 100% 판정된다.
- **내용 검증(자동)** = V4~V12·V14~V21
  → 결정적으로 잡히는 사실·정합성 위반만 본다. **해석의 명리학적 타당성을 보증하지 않는다.**

### 6.1 V15 강화 — 문단 분리 우회 차단

예전 V15 는 "양쪽 근거가 어딘가 인용됐고, 그 근거를 인용한 문단 중 하나에 조건 낱말이 있으면" 통과시켰다. 그래서 **한쪽은 §02, 다른 쪽은 §03** 에 나눠 두고 각 문단에 조건 낱말만 흩뿌리면 통과했다. 이제 **한 문단 안에서 양쪽을 함께 인용**해야 하고, 그 문단이 조건을 말해야 한다.

### 6.3 남은 한계 (검증기가 못 하는 것)

- V4 는 한자 쌍만 본다 — 한글 "갑자" 오류는 못 잡는다.
- V5 개수 검사는 숫자·한국어 수사("두 개")만 잡는다 — "정인이 둘" 같은 변형은 별도 규칙이 필요하다.
- V16·V19 는 보수적 휴리스틱이다. 근거 4개 이상을 붙인 문단은 오탐을 줄이려 통과시킨다.
- **문장이 명리학적으로 옳은지는 자동으로 판정하지 않는다.** V16 이 잡는 것은 "근거를 안 쓴 문단"이지 "틀린 해석"이 아니다.

  B 는 구조적으로 judge 4점에 묶였다. 이제 `chart.*` 도 개인 근거로 센다. 스텁 결과에서 B 의

- CA 분모는 각 실험군이 **볼 수 있었던** 의무만 센다(B 는 analysisData 가 없어 0/0 → 판정 보류).

## 8. 비용·실행 안정성 (P0-3)

- 단가: `claude-opus-5-5` 입력 $4 / 출력 $20 / 캐시 읽기 $0.20 (1M tokens). 캐시 쓰기 $5 는 가정값.
- 환율: 표시용 고정 1,390원/USD (`NYANG_USD_KRW` 로 변경).

| 항목 | 동작 |
|---|---|
| `--model` | 실제 API 호출(`ai.mjs`)까지 그대로 전달된다 |
| 모델 기록 | **요청 모델**(`requestedModel`)과 **응답 모델**(API `model` 필드, `responseModel`)을 모두 남긴다 |
| 단가 미등록 | `pricingKnown:false` · `costStatus:'unknown_pricing'` · `usd:null`. **0원으로 합산하지 않는다.** 합계는 `totalUsd:null` + `unknownPricingCalls` 로 보고 |
| 호출 전 최대 예상 비용 | 실행 전 전 픽스처×실험군의 (프롬프트 입력 토큰 추정 + `max_tokens` 전량 출력) × (1+재시도) 합계를 계산. `--max-cost-usd` 초과면 **호출 없이 exit 2**. 호출 직전에도 시도별로 다시 검사해 넘으면 그 호출을 차단(`phase:'blocked'`) |
| JSON 파싱 실패 | 응답을 받은 뒤 파싱이 실패해도 오류 객체에 `usage`·`ms`·`responseModel` 을 실어 보내 토큰·비용을 기록한다 |
| 예외 처리 | HTTP 4xx/5xx(`errorType:'http'`, `httpStatus`) · 네트워크(`network`) · 빈 응답(`empty_response`) · 본문 파싱(`bad_response`) · JSON 파싱(`json_parse`) · 출력 잘림(`stopReason:'max_tokens'` → `truncated:true`) |
| E 실행 조건 | 유효한 D 초안이 없으면 `skipped_no_valid_d` |
| 호출별 이력 | `out/<runId>/calls/<fixture>-<arm>-a<attempt>.json` — 시스템/사용자 프롬프트 전문, 재시도 feedback, 응답 상태·토큰·비용·검증 결과. `calls/index.json` 에 요약 |
| 예산 가드 | `--max-calls` · `--max-cost-usd`. 단가 미등록 호출이 생기면 남은 예산을 보장할 수 없어 추가 호출을 막는다 |

스텁의 비용은 **글자 수 기반 추정**이며 청구액이 아니다.

## 9. 블라인드 평가 자료 3종 (P1-1)

`out/<runId>/blind/` 에 생성된다. 한 파일에 다 담으면 평가자가 실험군·비용·자동 점수를 보고 판단이 흔들리고, 반대로 고객용에 근거가 남으면 '근거가 많다 = 좋은 해석'으로 읽힌다.

| 파일 | 공개 | 내용 |
|---|---|---|
| `blind-customer.md` / `.json` | 고객 평가자 | **해석 전문만**. 실험군·비용·자동 점수·근거 ID·모델명·명식·토큰 전부 숨김 |
| `blind-myeongri.md` / `.json` | 명리 검토자 | 명식·입력·해석 전문 + 문단이 인용한 **사실 값** + **규칙/KB 출처**(표기·원문 인용) |
| `tech-eval.md` / `.json` | 기술 평가자 | 실험군·요청/응답 모델·토큰·비용·지연·재시도·실패·구조/내용 위반 |
| `blind-key.json` | **비밀** | 표시 id ↔ 실험군 대응표(사례별 순서 포함)·모델·프롬프트 해시·설정·경계·A 콘텐츠 출처 |

- **표시 순서는 사례마다 무작위**다. 표시 id 는 `QA01-1`~`QA01-5` 처럼 사례별로 다시 매기고, 순서는 `hash(seed + 사례 id)` 로 정해 결정적이다(다시 돌려도 같음). 대응표는 `blind-key.json` 에만 있다.
- 이름은 `{name}` 로 마스킹한다. 토큰·비용은 고객·명리 패키지에서 뺐다(프롬프트 길이를 암시하므로).

## 11. 검토 요청 (구체적으로)

> 이번 판본에서 P0·P1 지적은 반영했다. 아래는 **반영 후에도 남는 판단**을 부탁드리는 항목이다.

1. **B 입력 보강이 공정한가** — B 가 대운·세운과 모델 자체 지식을 쓰는 것을 허용한 뒤에도, B/C/D 의 차이가 "analysisData → 지식베이스" 하나씩으로 유지되는가.
2. **V16 의 오탐/미탐** — "근거 ID는 유효하지만 문단이 그 사실을 안 쓴다"를 낱말·속성 대응으로 잡는 방식이 문장 스타일에 따라 오탐을 만들지 않는가. 4개 이상 근거 문단을 통과시키는 보수적 규칙이 적절한가.
3. **V17·V19·V20 의 정규식 한계** — 기둥 표기·원국/대운 혼동·시주 미상 판정이 실제 문장에서 놓치는 표현은 무엇인가.
4. **V21 의 판정** — "입력에 근거가 있는 섹션을 비웠다"가 정당한 축약(예: 앱 카탈로그에 그 주제가 없음)을 잘못 벌하지 않는가.
5. **A 콘텐츠 출처 구분** — §03·§08 을 `experimental-generated` 로 본 판단이 맞는가. A 가 실제 서비스보다 유리/불리해지는 지점이 더 있는가.
6. **블라인드 3종** — 고객용에 명식을 빼고 해석만 준 것이 평가에 충분한가. 명리용에 사실 값을 붙인 것이 평가자의 판단을 과도하게 이끌지 않는가.
7. **비교쌍 3종** — CP1~CP3 이 실험 질문을 다 덮는가. 필요한 쌍(예: 같은 일간·다른 성별, 같은 명식·다른 대운)이 더 있는가.
8. **비용** — 캐시 전략이 아직 없다. 12건 × 5실험군 × 재시도 + KB 27k 토큰 프롬프트가 현실적인가.
9. **지표** — judge 근사가 실제 품질과 상관 있을 만한가. 사람 평가 설계(3종 패키지)가 충분한가.
10. **지식베이스·문헌** — 35항목의 [문헌 확인] 인용이 원문과 맞는가(지난 리뷰 항목 유지).

## 12. 알려진 한계

- 오프라인 스텁은 **문장 품질을 재지 않는다**. 배선·검증기·채점·비용 경로만 검증한다.
- 자동 검증(V1~V21)은 결정적으로 잡히는 오류만 본다. **통과가 해석 품질의 보증이 아니다.**
- judge 는 결정적 근사이며 모델 채점·사람 채점과의 상관을 확인하지 않았다.
- V4 는 한자 쌍만 검사한다(한글 간지 오류 미검출).
- V16·V19 는 보수적 휴리스틱이다. 무관한 근거를 붙인 문단을 일부 놓칠 수 있다.
- E 의 "초안 대비 추가 사실" 검사는 여전히 없다(프롬프트 지시로만 막는다).
- `--mode full` 실호출은 승인 전까지 실행하지 않았다. 실제 비용·지연·품질은 미측정.
- O1(월령↔통근)은 QA01~12 에서 발동하지 않는다 — C1 픽스처로만 확인 가능.
